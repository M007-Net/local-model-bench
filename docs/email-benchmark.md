# Berkeley email classification

This objective test asks whether a model understands the primary purpose of a real email: company business, personal correspondence, personal messages in a professional context, logistics, employment, or document collaboration. It uses the [UC Berkeley annotated Enron corpus](https://bailando.berkeley.edu/enron_email.html), not the licensed 32-topic LDC corpus.

Berkeley released 1,702 emails annotated by two people. The local benchmark includes **950 emails** with exactly one nonempty coarse genre receiving at least two annotation votes. It excludes 464 cases without two-annotator agreement, 207 with multiple or missing genres, 22 empty-message genre cases, and 59 emails exceeding 16,000 characters (excluded whole, never truncated). No labels are inferred from mailbox folders or generated by a model.

## Prompt and scoring

The prompt lists all six categories and supplies complete email headers and body encoded as untrusted JSON data. It asks for exactly `{"genre_id":1}` with the chosen integer. The existing strict JSON equality checker rejects prose, code fences, string-valued IDs, extra fields, duplicate keys, and IDs outside 1–6. Each test allows 2,048 output tokens so reasoning-capable models can finish before giving the short answer.

Accuracy is correct predictions divided by all attempted responses. Macro-F1 averages per-category F1 over **all six categories**, assigning zero when a category's denominator is zero. Valid wrong predictions add false positives and false negatives; malformed answers and request failures add a false negative for the gold category. Warmups are excluded. Repeated waves and concurrent copies are repeated attempts. Incomplete runs are provisional. Coverage and per-category support are recorded, and the UI shows accuracy, macro-F1, and coverage.

The corpus is imbalanced, so macro-F1 helps expose a model that always chooses business. A five-email run may omit categories, depressing macro-F1 even with high accuracy. Use a larger count for comparisons. This is a local zero-shot protocol on historical email; it does not measure urgency, spam, action extraction, or guarantee performance on a modern inbox. Berkeley explicitly makes no general consistency or representativeness claim for its labels.

## Preparation and provenance

```powershell

npm run benchmark:email:prepare

```

Requires Python and the project's Node dependencies. The loader downloads Berkeley's public archive, reads `.cats` and `.txt` members without extracting archive paths, preserves complete message text (UTF-8 with Latin-1 fallback), applies the documented consensus filter, and sorts by source message ID. The TypeScript preparation step builds normal benchmark TestCases. The source archive hash, prepared dataset hash, exclusions and category counts are stored in `src/benchmark-data/berkeley-enron.manifest.json`. The prepared pack is included in the standard benchmark registry and desktop library.

Dataset source: Marti Hearst's UC Berkeley Enron Email Analysis project; annotation scheme and labeled messages released for the 2004 Applied Natural Language Processing course. ## Practice run

```powershell

$env:LMB_BASE_URL='http://127.0.0.1:11436'

$env:LMB_MODEL_KEY='lmb-email-gemma4-12b-16k:latest'

$env:LMB_COUNT='60'

$env:LMB_PACK_ID='berkeley-enron-challenge'

$env:LMB_SEED='42'

npm run benchmark:email -- output-directory

```

This uses the existing selection, validation, inference engine, objective checker, and report exporter. The exact model key must exist in the endpoint inventory. The engine sends one excluded warmup followed by the requested measured emails. Runs, errors, responses and metrics are saved incrementally to `email-run.json`; aggregate and per-category results go to `email-result.json` and `email-report.txt`. The CLI does not change the app's saved endpoint settings or explicitly unload external-server models. In the desktop app, select **Berkeley email classification** under **Benchmarks**.

## Challenge pack

**Berkeley email challenge** is a separate 120-email pack, 20 per category. It retains the original complete messages, prompts, and human gold labels. For each category it selects the 20 highest-ranked unique emails using a fixed text-complexity proxy: `log2(1 + body characters) + 2 × min(thread markers, 20)`. Thread markers include quoted lines and forwarded/reply headers in the body. Normalized full-message duplicates are removed before selection. Complexity is not a measured difficulty rating and is not chosen using candidate model responses.

Within this challenge pack, seed-based sampling shuffles each category, then interleaves them in a seeded category order. Every prefix has category counts differing by at most one. A 60-question run therefore contains exactly ten emails in each of the six categories. The desktop library defaults the challenge to 60 questions; all 120 are available. The original 950-email pack and its sampling stay unchanged.

The CLI now defaults to this challenge pack and 60 measured emails. Set `LMB_PACK_ID=berkeley-enron` and a smaller `LMB_COUNT` to use the original test. Results include per-category correct/attempted counts, F1, and a confusion matrix with gold categories as rows and predictions as columns. Invalid/failed outputs are excluded from the confusion matrix but still counted as misses in accuracy and F1. `email-mistakes.json` lists each failed case with gold/predicted IDs and the actual response for inspection. The desktop Results page shows a category breakdown table.

Rebuild the challenge alone using `node --import tsx scripts/prepare-email-challenge.ts`. Its manifest records the parent hash, deterministic selection scores, source item IDs, category counts, and the challenge hash. This is an intentionally selected challenge set; do not interpret its accuracy as representative of a normal inbox or directly compare it to the five-question smoke run as if the question sets were identical.

The challenge allows 8,192 output tokens and recommends at least 16,384 context tokens to avoid cutting off reasoning before the category answer. Managed LM Studio runs use that context automatically; an external server controls its own context, so check its actual loaded value. The interrupted 4K-context test is diagnostic only. The verified local run used a separate `lmb-email-gemma4-12b-16k` Ollama configuration built from the existing Gemma weights with `num_ctx=16384`; the original model defaults were preserved.

The challenge default request timeout is 600 seconds; set `LMB_TIMEOUT_SEC` to change it. An interrupted CLI run can be continued using `LMB_RESUME_FILE` pointing to its checkpoint. Resume requires identical model, endpoint, full questions, and generation settings; only timeout may change. It retains completed answers even when they are wrong, retries failed/unfinished cases, and records the deadline change in run metadata. Diagnostic failed attempts are kept separately from final measured results.
